# 需求与业务规则

本文是本版功能范围和业务行为的依据。字段和接口结构只在 [api.md](api.md) 定义，技术与模块边界只在 [architecture.md](architecture.md) 定义。

## 1. 使用场景与交付

普通用户查看汕头真实景点参考资料，填写旅游天数、偏好和门票预算，获得分日草案；调整、检查后确认保存，之后可查看或删除。第一版固定汕头，资料人工维护、不保证实时。管理员在分析模型中维护景点资料，最小原型通过编辑数据文件实现，不开发管理后台。

首要交付是按教学安排完成各次 UML 实验与报告。本版原型的开发范围固定为下表；如原型不能按计划完成，保留真实进度，不影响课程建模的独立交付。

| 编号 | 功能 | 原型范围 | 负责人 |
| --- | --- | --- | --- |
| F01 | 查询景点 | 按类别或关键词查询汕头景点参考资料 | B |
| F02 | 填写旅游需求 | 城市固定汕头，填写天数、类别偏好和门票预算 | B |
| F03 | 生成草案 | 规则或单 Agent 推荐，返回同一草案格式 | B 负责入口与 Agent；A 的规则服务供其调用 |
| F04 | 调整草案 | 展示每日安排，添加、删除或移动景点并重新校验 | A |
| F05 | 保存与管理 | 确认保存、列表、详情、删除；不要求修改已保存记录 | A |
| F06 | 维护景点资料 | 通过受版本管理的样例文件维护；不宣称已实现管理员页面 | B |

F03 的两个生成服务各有完整负责人：A 独立完成确定性的规则推荐，B 独立完成 Agent 推荐。B 在生成入口根据模式调用对应服务；并非将一次模型执行拆给两人实现。

## 2. 已确定的业务规则

| 编号 | 已确定规则 |
| --- | --- |
| BR01 | 单机、单用户、单后端进程演示；没有注册、登录、权限隔离或多人使用承诺 |
| BR02 | 城市固定汕头；天数为 1–5 的整数；预算为非负整数，单位人民币元；前后端均校验，后端为准 |
| BR03 | 类别为“自然”“人文”“休闲”；偏好可空，可多选，重复项去重；偏好是软约束，可安排同城市其他类别并提示 |
| BR04 | 每份草案恰好包含第 1 天至所选天数，每天至多 2 个景点；同一景点不重复，必须属于所选城市；允许个别日期空白，但必须提示，全部为空不可保存 |
| BR05 | 模型只能使用本次查询工具返回的 ID；不存在、重复、跨城市或未查询到的 ID 视为无效输出，不自行补造 |
| BR06 | 费用只计已知的参考门票，由后端依据数据计算；未知票价不按免费处理，预算是否满足须标记待确认；不包含交通、餐饮和住宿 |
| BR07 | 超预算允许显示和保存，但必须明确提示；不保证最优路线、时段可行性或预算一定满足 |
| BR08 | 草案只有点击确认保存后才持久化；调整后的草案保存前再次校验；同一按钮请求进行中不重复发送 |
| BR09 | 已保存记录包含服务端 ID、创建时间和保存时景点及门票快照；查看历史不按现价重算；删除后查询返回不存在 |
| BR10 | Agent 与规则结果来源明确；Agent 出错不静默改用规则，用户主动选择；规则模式无需密钥、网络或模型初始化 |
| BR11 | Agent 只提供一次只读城市景点查询，最多两次模型调用；不写文件、不保存行程、不使用长期会话或自动重试 |
| BR12 | 错误与未完成状态如实展示；模型文本作为普通文本显示，不当作 HTML 或脚本执行 |
| BR13 | Agent 根据景点区域和参考游览时长安排，每日提供简短时段建议与理由；一天最多 480 分钟参考游览时长，南澳与非南澳景点不安排在同一天。时间不包含实时交通判断 |

规则模式按偏好匹配优先、每组 ID 升序遍历汕头景点。每个景点选择符合 BR13 且未满两处的一天：优先已有同区域景点的那一天，其次选景点数较少的一天，再按天数升序；无可用日期则跳过。输入相同、资料相同则结果相同；没有偏好匹配或日期不足时按返回的警告说明。

## 3. 状态与失败

行程业务状态为“草案 → 已保存”；取消编辑是丢弃草案，不创建记录；删除是删除保存记录，不保存“已删除”状态。页面加载中、调用失败等属于界面或执行状态，不当作行程业务状态混进类图。

生成失败时显示错误，草案不自动保存；可以保留用户当前输入和旧草案，但旧草案不得标成新生成结果。用户调整尚未通过校验时标为待校验，保存前必须校验当前版本，防止旧请求覆盖新修改。

景点或历史文件不可解析时返回存储错误并保留原文件；没有历史文件时按空列表处理。保存失败不能显示成功。少量本地资料不做分页、缓存或后台任务。

## 4. 固定不做的内容

实时地图、天气、交通、联网爬取、在线预订及支付、大规模景点资料、登录和管理员后台、精细交通路线、完整旅游总预算、统计和导出、多 Agent、RAG、审批恢复、长期记忆、流式聊天、自动部署及 CI。

本版确定文件持久化，不在开发途中追加数据库。后续确需启用原方案的 PostgreSQL/SQLAlchemy 时作为单独版本，先评估现有 API 兼容性与时间；不能要求当前开发者同时维护文件与数据库两条路径。

## 5. 课程材料边界

指导书中的实验一允许选题并描述目标和功能；实验二至六分别围绕用例、类、活动、状态与时序建模，实验七综合整理。模型覆盖和图表数量遵循教师要求，不把本方案建议当作教师规定。

实验七指导书使用语音播放器作为示例，沿用自选题目的安排以教师要求为准。实验八 SVN 为另一项练习，是否要求完成按课程安排处理。本方案不自行增加答辩、页数或软件实现的课程硬性要求。
