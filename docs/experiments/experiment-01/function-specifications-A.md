# 成员 A 功能简述

下列两表为实验一正式功能简述；均为需求设计，尚未实现。

## F02 填写旅游需求

| 字段 | 内容 |
| --- | --- |
| 功能名称 | 填写旅游需求 |
| 功能编号 | F02 |
| 操作者 | 普通用户 |
| 功能简述 | 用户以汕头为固定目的地，填写旅游天数、兴趣偏好及参考门票预算，提交行程规划需求。系统检查输入是否合法并提示修正。 |

输入：固定目的地汕头；1–5 的整数天数；自然、人文、休闲类别偏好，可不选，重复项去重；以人民币元为单位的非负整数预算。输出：通过校验的规划需求。异常：非法天数、预算、类别或非汕头目的地应提示更正，不进入生成流程。界面可固定城市，后端仍校验；保留现行 `city` 字段。

## F03 生成行程草案

| 字段 | 内容 |
| --- | --- |
| 功能名称 | 生成行程草案 |
| 功能编号 | F03 |
| 操作者 | 普通用户 |
| 功能简述 | 用户提交需求后，系统依据汕头预置景点资料生成分日行程草案，展示参考门票估算和必要提示，由用户决定是否调整或确认保存；生成本身不保存行程。 |

输入：F02 合法需求及用户选择的规则或可选 Agent 方式。输出：分日草案、门票小计与合计、预算及数据不足提示。每天最多两个景点，全程不重复，仅使用汕头本地资料。超预算可展示并由用户确认保存；部分空白日期须提示，全空草案不可保存。

异常：资料缺失或损坏应报告；模型不可用、超时、未真实查询或输出非法编号时明确失败，由用户主动选择规则方式。模型费用不作为依据，程序重新计算。正式接口错误结构继续使用 `docs/api.md`。

F01、F04、F05、F06 的正式功能表由 B 独立提交，再由 A 合并；本文件不替代 B 的交付。
